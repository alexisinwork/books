## CRLF/LF і хеші маніфестів томів 0, 4, 5 (маніфести не змінювалися)

**Проблема.** `.gitattributes` задає `* text=auto`, локально `core.autocrlf=true`. Git зберігає `.txt` з LF (`git ls-files --eol`: `i/lf w/crlf`), а робоча копія в Windows має CRLF. Для т. 0, 4, 5 значення `target_txt_sha256` у `manifest.json`, `canonical_ua_master.sha256` у `book.json` і `language-editions.json` пораховано від робочої CRLF-копії (`0db25fda…`, `d2701ec4…`, `838a4242…`). Для т. 1–3 навпаки: записано хеш LF-blob (`8b8d5b55…`, `a7750dd5…`, `50652944…`), який не збігається з робочою копією в Windows. Отже, у будь-якому середовищі половина перевірок дає хибне «не збігається»: у Windows — т. 1–3, на GitHub або в Linux-чекауті — т. 0, 4, 5. Та сама розбіжність є в посиланнях `canon.json` і в `supersedes` у `book-04/book.json` (там `94de802a…` — хеш blob-у).

**Варіант рішення (потрібне погодження автора):**
1. Конвенція: SHA-256 рахується від **LF-вмісту, як його зберігає Git** (`git show HEAD:<path> | sha256sum` або `tr -d '\r' < file | sha256sum`). Такий хеш однаковий на всіх платформах.
2. Додати в `.gitattributes` правило `**/editions/**/*.txt text eol=lf` (або `-text`), щоб робоча копія в Windows теж мала LF. Тоді `sha256sum file` збігатиметься з маніфестом. Після цього один раз виконати `git add --renormalize`.
3. Окремим комітом перерахувати `target_txt_sha256` / `canonical_ua_master.sha256` для т. 0, 4, 5 у `manifest.json`, `book.json`, `language-editions.json` і хеш ред. 07 у `canon.json`. Старі CRLF-хеші зберегти в полі на кшталт `sha256_crlf_legacy`, щоб не зламати посилання в старих аудитах.
4. Додати в механічну перевірку крок нормалізації CRLF→LF перед хешуванням.

Томи 4–5 зараз ревізують інші агенти, тому пункт 3 для них краще виконати після прийняття ревізій literary-08/07.
